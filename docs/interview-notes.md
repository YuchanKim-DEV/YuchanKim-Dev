## 1. 트레이드오프 판단 사례

### 대표 사례 — 서버 2대 환경의 중복 처리 차단 (Project 4)

**🎤 1분 답변**

> **상황** — 상담 분석 파이프라인을 서버 2대로 운영하고 있었는데, 상담사가 분석 요청 버튼을 한 번 더 누르면 같은 통화가 두 번 처리됐습니다. 처음엔 메모리 Map으로 막았지만, 서버가 2대라 서로의 Map을 보지 못해 서버가 갈리면 중복이 그대로 통과했습니다.
>
> **첫 번째 판단 — 어디서 막을 것인가** — 정석은 기존 결과 테이블에 유니크 인덱스를 거는 것이었습니다. 하지만 이미 운영 중인 대용량 테이블이라 인덱스 추가 중 락이 걸리면 실시간 서비스가 멈출 수 있었습니다. 그래서 정석 대신 운영 안정성을 택해, 기존 테이블은 건드리지 않고 처리 중인 통화만 담는 작은 전용 테이블을 만들었습니다.
>
> **두 번째 판단 — 어떻게 판정할 것인가** — "조회 후 없으면 넣기"는 두 서버가 동시에 "없음"을 볼 수 있어서, `INSERT IGNORE`의 영향 행 수로 판정했습니다. DB가 한 건만 통과시키므로 별도 분산 락이 필요 없었습니다.
>
> **세 번째 판단 — DB가 죽으면?** — 판정 자체가 실패하면 통과시키는 fail-open으로 설계했습니다. 중복은 나중에 정리할 수 있지만 통화 유실은 복구할 수 없기 때문입니다. 처리 도중 서버가 죽은 통화가 영원히 막히지 않도록 TTL이 지나면 다른 서버가 이어받게 했습니다.
>
> **결과** — 운영 테이블을 한 번도 바꾸지 않고 서버 간 중복을 원자적으로 차단했습니다.

**예상 꼬리 질문**

| 질문 | 답변 포인트 |
|---|---|
| fail-open이면 결국 중복이 생기지 않나요? | 맞습니다. 그래서 저장 쪽을 upsert와 "재등록 시 기존 결과 삭제 후 재저장"으로 멱등하게 만들어, 중복이 들어와도 최종 데이터는 1건으로 유지됩니다. |
| TTL 15분은 어떻게 정했나요? | STT · 분류 · 요약 전체 처리가 끝나는 시간을 기준으로 잡았습니다. *(실제 근거 확인 필요)* |
| Redis 같은 분산 락은 고려하지 않았나요? | 새 인프라를 추가하지 않고, 이미 두 서버가 공유하는 DB의 PK 제약으로 해결하는 편이 운영 부담이 적다고 판단했습니다. |
| 왜 기존 테이블에 인덱스를 못 걸었나요? | 운영 중인 대용량 테이블이라 DDL 중 락으로 서비스가 멈출 위험이 있었고, 운영 DB라 기존 테이블 변경 자체가 어려웠습니다. 직접 판단해 배제했습니다. |

### 다른 트레이드오프 사례 (2순위)

- **마스킹을 통화 단위로 바꾼 것 (Project 3)** — 정확도를 80% → 98%로 올리는 대신, 통화가 끝날 때까지 마스킹 전 원문이 *암호화된 상태로* DB에 잠시 남는 비용을 감수했습니다.
- **유실 대신 중복을 택한 커밋 전략 (Project 3)** — DB 저장이 끝난 뒤에만 오프셋을 커밋해, 재처리 시 중복 가능성은 있지만 유실은 없도록 했습니다(at-least-once). 중복은 upsert로 흡수합니다.

## 2. 프로젝트별 문제 해결 이야기

### Project 1 · 해외 콜센터 STT 서비스 확장 (2026.09 ~ 진행 중)

- 프로젝트 메인 담당으로 고객사 요구사항을 조율하며 진행 중
- 국내 버전과 달리 통화 종료 후 결과가 한 번에 묶여 들어오는 배치형 이벤트 구조에 맞춰 컨슈머를 재설계하고, 테스트 환경에서 실데이터로 검증
- 마스킹은 STT 엔진에서 호출하도록 변경 예정

### Project 2 · 실시간 상담 음성 스트리밍 STT 연동 시스템 (2026.02 ~ 2026.06)

**① STT 엔진 부하 쏠림 — 최고 CPU 200% → 80% 이하**
- **발견**: 배포 후 AWS에서 task별 CPU를 모니터링하다 한 task만 200%를 쓰는 것을 발견. gRPC가 느려지며 지연과 누락으로 이어짐
- **원인**: gRPC는 HTTP/2 연결 하나를 오래 재사용하는데, 로드밸런서(NLB, L4)는 연결 단위로만 분산해 한번 연결된 서버로 통화가 계속 몰림
- **시행착오**: 연결을 여러 개(채널 풀)로 늘려 가장 한가한 채널에 배정했지만, 연결이 유지되는 한 쏠림이 다시 생김
- **해결**: 채널을 주기적으로 새로 맺어 로드밸런서가 서버를 다시 고르게 하고, 기존 채널은 진행 중인 통화가 끝날 때까지 기다렸다 닫음(DRAINING)

**② 결과 전달 지연 — LAG 10,000건 이상 → 평시 0건(평균 3~10건)**
- **원인 1**: 응답을 기다리는 동기 호출(`.block()`)이라 처리량이 부족
- **원인 2**: `prematurely closed` — 상대 서버가 이미 끊은 유휴 연결을 커넥션 풀에서 꺼내 재사용
- **원인 3**: 새벽처럼 메시지가 없을 때 NAT 게이트웨이가 유휴 TCP 연결을 끊어, 파티션은 할당돼 있는데 소비가 멈춤
- **시행착오**: 재시도 횟수만 늘렸지만 동기 구조에서는 지연이 해소되지 않음
- **해결**: WebClient 비동기 호출 + 큐별 동시 요청 수 제한, 유휴 연결 시간 단축과 백그라운드 정리, 연결 오류만 지수 백오프 재시도, Kafka 연결 keepalive 설정

**③ 상담사 전환 시 대화 섞임**
- **증상**: 통화가 다른 상담사로 넘어가면 대화 순서가 뒤섞이고, 이전 상담사 대화에 섞여 들어가며, 중복 번호로 전달이 거절됨
- **원인**: 전환 시 통화 ID는 그대로인데 연결이 끊겼다 다시 맺어지며 문장 번호가 어긋남
- **해결**: 통화 · 상담사 · 채널 단위로 문장 번호를 직접 다시 매기고, 중복 시작 이벤트 제거. 같은 통화는 한 워커가 순서대로 처리

### Project 3 · 실시간 상담 STT 수집 플랫폼 (2025.12 ~ 2026.02)

**① 금칙어 검사 지연으로 LAG 누적 — 30s → 50ms (약 600배)**
- **원인**: 직접 개발한 금칙어 엔진(Python, Aho-Corasick)이 호출마다 키워드 100만 건으로 오토마톤을 새로 생성해 건당 30초 소요
- **해결**: 오토마톤을 메모리에 캐시해 재사용 → 50ms로 단축, LAG 해소

**② 개인정보 마스킹 정확도 — 80% → 98%**
- **원인**: 문맥으로 판단하는 NLU 엔진에 문장을 하나씩만 보내, 여러 문장에 걸친 개인정보를 판단하지 못함
- **해결**: 통화 종료 시점에 통화 전체를 합쳐 한 번에 요청하고, 결과를 문장별로 다시 나눠 일괄 업데이트 (마스킹 엔진은 다른 파트, 연동 방식을 변경)

**③ 24시간 서비스의 배포 · 종료 시 유실 위험 — 누락 문의 0건**
- **상황**: 24시간 통화가 들어와 jar 교체나 종료 때 처리 중이던 데이터가 사라질 위험
- **시행착오**: 리스너에 stop을 요청해도 한 번에 멈추지 않는 경우를 실제로 겪음 (내부 큐가 가득 차 리스너 스레드가 대기 중이면 stop이 끝나지 않음)
- **해결**: 신규 유입 차단 → stop · pause · 재시도, 끝내 안 멈추면 내부 진입 차단 → 내부 큐와 처리 중 작업이 0이 될 때까지 대기 → 워커 종료. 배포 전 호출하는 drain API 제공, DB 저장 성공 후에만 오프셋 커밋
- **근거**: 고객사가 오픈 이후 매일 무작위 1,000건을 검수하는 환경에서 누락 문의 0건

**PoC 때의 교훈**: 파티션 번호와 워커를 고정 매핑했더니 한 통화의 메시지가 여러 워커에서 처리돼 통화 종료가 먼저 처리되고 늦게 온 문장이 유실됨 → 통화 ID 해시 기준으로 같은 통화는 한 워커가 순서대로 처리하도록 변경

### Project 4 · 상담 AI 분석 파이프라인 (2025.08 ~ 2025.12)

**구조**: 요청 API가 요청 토픽에 Produce → AI 파트가 Consume해 STT · 분류 · 요약 엔진을 호출하고 결과 토픽에 Produce → 결과 컨슈머가 Consume해 DB에 저장. 결과가 빈 값이거나 오류면 결과 컨슈머가 엔진을 직접 호출해 저장

**① 하루 2만여 건 결과 누락 장애 → 이후 누락 0건**
- **상황**: 오픈 이후 다른 파트에서 전달해야 할 분류 · 요약 결과가 주기적으로 누락
- **시행착오**: 처음엔 수동으로 메움 → 하루 약 2만 건 누락 장애 발생 → 기간 단위 복구 앱을 만들어 누락분 복구
- **해결**: 사후 복구에 그치지 않고, 빈 값 · 오류 수신 시 엔진을 직접 재호출하는 실시간 재시도 추가 (전용 스레드풀, 최대 3회, 최종 실패는 별도 로그)

**② 서버 2대 환경의 중복 처리** → [1. 트레이드오프 판단 사례](#1-트레이드오프-판단-사례) 참고
- **원인**: 요청 경로가 두 곳이라, 자동 전송된 통화를 상담사가 수동으로 한 번 더 요청

**③ 모든 대화가 상담사로 저장되는 버그 — 화자 구분 85% → 90%**
- **발견**: 운영 중 상담 이력을 직접 확인하다 발견
- **원인**: 엔진의 화자 표기 형식(`SPEAKER_00`)이 코드 기준(`SPEAKER_0`)과 달랐고, 발화 수 비교 방식은 동수일 때 한쪽으로 쏠리는 결함이 있었음
- **해결**: 표기 정규화, 발화 수 비교 제거, 기본 매핑에 상담사 확정 멘트 보정 추가 (애매하면 판별을 포기해 오판 방지)
- **한계**: 화자 구분은 엔진 개선이 필요한 영역이라 목표 96%는 미달. 엔진 업데이트가 막힌 상황에서 애플리케이션 규칙으로 올릴 수 있는 만큼 올림

## 3. 자주 나올 기술 질문과 원리

| 질문 | 핵심 답변 |
|---|---|
| gRPC 부하가 왜 한 서버로 쏠렸나요? | L4 로드밸런서는 연결 단위로 분산하는데, gRPC는 HTTP/2 연결 하나를 오래 재사용하기 때문 |
| 왜 새벽에만 소비가 멈췄나요? | NAT 게이트웨이의 유휴 연결 타임아웃(약 350초)으로 연결이 조용히 끊겼기 때문. keepalive와 `connections.max.idle.ms`를 더 짧게 설정 |
| `prematurely closed`는 타임아웃인가요? | 아닙니다. 응답 전에 상대가 연결을 먼저 끊은 것. 상대가 닫은 유휴 연결을 재사용해서 발생 → 유휴 시간을 상대보다 짧게, 연결 오류만 재시도 |
| Kafka 컨슈머에 Tomcat이 필요한가요? | 아닙니다. Kafka는 자체 TCP 프로토콜. `spring-boot-starter-web`을 넣으면 내장 Tomcat이 함께 올라올 뿐 |
| MVC 앱에서 Netty를 쓸 수 있나요? | 네. Netty는 독립 라이브러리라 MVC(Tomcat, HTTP)와 별개 포트로 TCP 서버를 직접 띄울 수 있음. WebFlux가 Netty를 쓰는 것이지 그 반대가 아님 |
| at-least-once는 어떻게 보장했나요? | 자동 커밋을 끄고, DB 저장 성공 후에만 수동 커밋. 중간에 죽으면 재기동 후 다시 처리 |
| 같은 통화의 순서는 어떻게 지켰나요? | 통화 ID 해시로 내부 큐를 나눠, 같은 통화는 항상 같은 워커가 순서대로 처리. 다른 통화끼리는 병렬 |
| stop이 왜 한 번에 안 되나요? | `stop()`은 요청일 뿐이고, 리스너가 처리 중인 레코드를 끝내야 멈춤. 큐가 가득 차 `put()`에서 대기 중이면 끝나지 않음 |

## 4. 답변 원칙

- **"무엇을 택했나"보다 "무엇을 포기했고, 그 비용을 어떻게 메웠나"**까지 말한다
- 숫자는 근거와 함께 말한다 (예: 누락 0건 → 고객사 일일 1,000건 검수 기준)
- 목표를 못 채운 것도 숨기지 않고, 한계와 그 안에서 한 최선을 말한다
- 내 파트와 다른 파트의 경계를 분명히 말한다 (예: 마스킹 엔진은 다른 파트, 나는 연동 방식을 변경)
